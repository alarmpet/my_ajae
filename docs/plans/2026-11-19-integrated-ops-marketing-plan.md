### 4.2 승인 한 건의 단위와 기록

1. **미리 보기 생성.** `slot_id`, KST 시각, 플랫폼·예상 계정, 실제 캡션과 이어지는 글, 미디어 파일의 순서·SHA-256, AI 고지, 장부·정책 SHA를 묶는다. 확인 화면은 이 출력 계획을 그대로 사용하고, `manifest_sha256`으로 내용을 고정한다.
2. **묶음 승인과 최종 확인.** 묶음 승인 기록은 콘텐츠 바이트를, 슬롯 확인은 `slot_id`·시각·계정·플랫폼·`manifest_sha256`·확인 시각을 가리킨다. 사용자의 「올려」를 기록하는 창구는 기존 채팅을 사용한다. 직전 확인의 유효 시간은 현행 알림 창을 활용해 **슬롯 전 120분 이내**로 제안한다. 이 값은 상시 운영 전 사용자 결정으로 확정한다.
3. **한 번씩 실행.** `slot_id + platform`마다 예약을 선점하고, 같은 글 ID가 해당 플랫폼에서 이미 발행된 경우 새 슬롯에서도 게시를 막는다. 원격 게시 ID는 발행 결과에 따로 적는다. SQLite는 다중 작업에서 트랜잭션과 고유 키가 필요한 발행 상태에만 후보로 두고, 기존 JSONL은 기록 조회·내보내기 호환에 유지한다. 게시 전 상태는 `확인 필요 → 실행 가능 → 시도 중`, 게시 후 상태는 `게시 확인`, `일부 완료`, `결과 미확인`, `실패`, `놓침`으로 기록한다. 각 상태에는 이유와 마지막 확인 시각을 붙인다.
4. **재시도와 복구.** 미디어 업로드나 컨테이너 생성 전 연결 실패는 실패 단계와 재시도 가능 여부를 기록한다. 원격 발행 직후 응답이 유실됐으면 원격 계정·시각·컨테이너·콘텐츠를 대조한다. 대응 건을 특정할 수 없으면 담당이 확인할 때까지 보류. 본글이 확인된 뒤 이어지는 글이 실패하면 남은 조각만 보인다. R2 정리 실패는 링크 확인·게시 상태와 독립적으로 다룬다.
5. **짧은 주기 실행.** `--tick`이 매번 일정을 새로 읽고 기한 내 슬롯만 잡는다. 시각 이후 재실행 허용 창은 5분을 초기 제안으로 둔다. 이 창을 넘거나 계정·정책·확인에 문제가 있으면 보류·놓침을 기록한다. 다음 슬롯은 독립적으로 처리한다. 로그인 자동 실행을 교체할 때는 기존 프로세스 종료와 새 작업 시작을 대조하고 가짜 계정 어댑터로 먼저 24시간 돌린다. [Microsoft 작업 스케줄러 설정](https://learn.microsoft.com/en-us/powershell/module/scheduledtasks/new-scheduledtasksettingsset?view=windowsserver2025-ps)

### 4.3 정책·공개 경계

- `check_post`는 자동 선별이다. 숫자와 ID가 통과하더라도 문장과 근거의 의미가 같다는 사실은 초안 검토에서 확인한다. 예를 들어 `73,414일 대조`와 `풀이가 맞는다`는 별개 주장이다. `allow_numbers`를 통해 승인 예외를 쌓기보다, 공개할 숫자의 출처와 단위를 장부에 먼저 보강한다.
- 확인 문구 원문·실패 원문·토큰 이름과 만료 상태·내부 경로는 운영 로그에 필요한 최소만 남긴다. 현재 `CONFIRMED.jsonl`은 Git 추적 중이며 승인 문구를 기록한다. 앞으로 공개 기록에는 규칙·결과·게시 주소 등 공개할 값만 남기고, 향후 상세 승인 이력은 로컬에 저장한다. 과거 이력 정리는 실제 포함 내용을 점검한 뒤 별도 결정한다.
- `secret_store.py`를 쓰는 운영 경로가 있고 `.env`도 존재한다. 사용처별 비밀값의 **존재·만료·예상 계정만** 읽는 점검을 만든다. 다른 채널의 R2 자격을 공유하는 경로는 운영 의존성으로 기록하고, 해당 자격의 존재와 최소 접근 범위는 담당이 확인한다. 네트워크 오류 로그는 토큰·웹훅 주소와 응답 본문을 정리해 기록한다.
- Slack은 당장은 알림과 업무 선택 안내에 사용한다. `slack_notify.notify()`는 모든 알림에 멘션을 붙인다. 묶음 승인과 슬롯 확인 외의 요청을 한 장으로 모으고, 성공 알림은 멘션 없이 집계한다. 관리 작업의 마지막 성공 시각을 보고한다. PC가 꺼진 상태의 알림이 꼭 필요해지면 별도 감시 지점이 필요하다. Slack의 양방향 버튼은 웹훅에 더해 이벤트 수신 설정이 필요하므로 실제 응답 시간 절감이 확인될 때 검토한다. [Slack 웹훅](https://docs.slack.dev/messaging/sending-messages-using-incoming-webhooks/) · [Slack Socket Mode](https://docs.slack.dev/apis/events-api/using-socket-mode/)

먼저 용하네·보카 각 3건을 표본으로 뽑는다. 사건 원문을 커밋에서 열 수 있고, 글·카드·영상의 각 사실이 같은 사건의 근거를 가리키면 통과다. 기존 글에 여러 사건이 섞였으면 다음 편집 때 범위를 하나로 좁힌다. 연구 자료는 반복되는 불편을 고르는 데 쓰고, 표본을 전체 시장 비율로 확대하거나 남의 사용자 후기를 우리 이용자 후기처럼 쓰지 않는다. [소재 장부](../../ledger/README.md) · [리뷰 조사와 표본 범위](../research/2026-11-15-saju-app-reviews.md)

### 5.3 카드·영상 제작과 보관

**기본 산출물은 실화면 한 장 또는 승인된 짧은 글**로 시작한다. `make_card.py`와 `make_hook_cards.py`를 재사용해 템플릿과 글 문구를 분리한다. 현재 `make_hook_cards.py`의 `ART`는 특정 글 ID에 붙어 있고 `flow-images.mjs`는 경로 치환과 화면 상태에 의존한다. 다음 제작분부터 입력 폴더와 글꼴 경로를 설정으로 확인하고, `ffprobe`·이미지 메타데이터로 비율·해상도·재생 시간·오디오 유무를 체크한다. 공개 전 실제 값, 글자 겹침, 화면 개인정보, 고지는 사람이 확인한다.

영상은 새 렌더러를 만들기 전에 `D:\motion-studio` 또는 auto-cf의 기존 제작 경로에서 **한 편**을 비교한다. 인계서 한 장에 `event_id`, 화면 출처 SHA, 캡처 범위, 자막, 고지, 원하는 형식, 회수할 파일을 적는다. 실화면이 필요한 장면을 생성 그림으로 교체하지 않는다. 입출력 경로와 글꼴·FFmpeg·Pillow·boto3를 사전 점검하되, 텍스트 글은 제작 도구 장애의 영향을 받지 않게 한다. 제작·사람 검수·렌더 시간을 각각 잰다.

승인받은 최종 파일은 내용 지문을 키로 하는 작업 폴더에 묶어 저장한다. Git 밖 백업에는 승인용 파일과 허용된 출처 메타데이터를 함께 둔다. 작업 폴더가 사라져도 같은 지문의 본문·카드를 복원하면 통과다. 복원한 파일이 다르면 새 승인으로 간다. 근거. [훅 카드 제작 절차](../../.claude/skills/hook-card/SKILL.md) · [카드 도구](../../tools/make_hook_cards.py) · `D:\motion-studio` `8afe57c:README.md`.

## 6. 프로젝트별 홍보 운영

**배분 제안.** 첫 2주는 용하네·보카를 중심으로 게시 준비를 주 7칸 이내에서 묶는다. 만드는 과정·따라 하기·대화·앱 소개의 균형은 `week-plan` 비율을 참고한다. Threads는 검증된 짧은 사건과 대화 주제, Instagram은 화면이 설명이 되는 카드나 릴스에 우선 적용한다. 겹치는 주제가 있어도 **비교하려는 변수 하나**를 미리 정한다. 유튜브·틱톡·X는 계정·권한·비용 부담과 성과를 대조한 뒤 확장 순서를 정한다.

**실험 예시.** 보카라이더의 첫 판 소재 두 쌍을 같은 채널·비슷한 요일과 시각에 배치하고 첫 1~2줄만 `실제 결과 먼저`와 `어려웠던 지점 먼저`로 비교한다. 글마다 앱·행동·카드 형식은 맞춘다. 조회/도달과 완료 행동을 각각 본다. 표본이 작고 시기가 다르면 사례로 남긴다. 용하네는 훅 문구 실험 전에 예시 페이지가 열린다는 점을 확인하고 링크→열기 구간부터 잰다.

## 7. 숫자와 의사결정

### 7.1 지금 아는 것과 측정 부족

11월 17일 저장한 스냅샷에서 Threads 본글 14개의 조회는 **3~80, 중앙값 30**, Instagram 본글 14개의 도달은 **0~114, 중앙값 0**, 그중 10개가 기록상 0이다. 플랫폼별 조회/도달 정의와 글 나이가 다르고, Instagram 0이 어떤 조건에서 기록됐는지는 확인하지 못했다. 최근 데이터 74줄은 전체 28개 글·플랫폼 조합을 여러 번 본 값이다. 이 숫자만으로 포맷의 우열이나 클릭·완료 효과를 판정하기 어렵다.

`post_metrics.py`는 게시 기록의 각 본글을 모두 조회해 관측을 추가하고, 현재 초안에서 `pillar`, `hook`, 첫 문장을 읽는다. 게시 뒤 초안이 바뀌면 당시 실험 분류도 바뀔 수 있다. 앱 이동·완료, 동일 관측 창, 직접 단 첫 댓글과 본문 분할의 보정은 자동화돼 있지 않다. `--dry`도 API를 읽는다. Meta가 엔드포인트별 권한을 요구하므로 계정에서 지원하는 항목·권한·결과 필드를 실제 확인하고, 조회 실패와 0을 분리한다. 링크 모음은 작게 시작한다. 앱별 목적지를 목록으로 고정하고 날짜·앱·가능한 경우 채널 단위로 이동 건을 남긴다. 새 링크 구축 환경과 무료 한도는 구현 직전에 공식 문서로 확인한다. 공개 페이지를 띄우기 전에 잘못된 앱 키, 외부 목적지 오입력, 실제 폰 열기, 수집 실패 시 이동 가능 여부를 시험한다. 완료 이벤트가 없는 동안 보고서에는 **이동 클릭까지** 보여 준다. 앱 쪽 수집이 필요하면 프로젝트 담당에 요청한다.

관측 키는 `platform + remote_post_id + window`로 제안한다. 원본 게시 문안·앱·기둥·훅·형식은 게시 시점에 고정한다. 24시간 창은 예를 들어 24~30시간, 72시간 창은 72~84시간에서 첫 성공 관측을 채택한다. 정확한 관측 시각을 넘겨 수집했으면 `지연`을 표시한다. 같은 창 재시도는 기존 성공값을 중복 합산하지 않는다. 과거 JSONL의 관측은 날짜 단위 자료로 유지한다.

### 8.1 구현과 시험 사이의 계약

- **검사.** `check_post.mjs`는 `PASS / HOLD / FAIL`과 별도 안내를 기계가 읽을 수 있게 제공한다. 신규 글은 장부 기본 사건 하나와 그 사건의 보조 출처를 구분한다. 테스트는 정책 파일 없음, 새 규칙, 대상 앱 다른 사건, 철회, 문장 숫자와 단위, 게시할 최종 캡션, 카드 문구를 포함한다. 이미 올라간 글은 검사 결과만 기록한다. 기본 시험 명령은 `node --test tools/check_post.test.mjs tools/check_post.sabotage.test.mjs`다.
- **실행.** `--show`는 네트워크 없이 채널별 최종 계획을 출력한다. `--confirm`은 보여 준 계획과 슬롯을 받아 시각과 함께 기록한다. `--tick`은 같은 계획을 검증해 유효한 슬롯만 실행한다. 기존 명령을 유지할 때도 같은 실행 검사와 잠금을 거치게 한다. CLI 시험은 내부 가짜 어댑터와 임시 폴더에서 실시한다.
- **관측.** 아침 점검은 `read status → render summary → send → save delivery state` 단계를 분리한다. 원격 갱신 실패, 요약 저장 실패, Slack 장애, 일정 없음의 차이가 출력된다. 실제 Slack·스케줄러 운영 시험에서는 별개 테스트 일정으로 먼저 확인한다.
- **전환·되돌리기.** 기존 승인·게시 JSONL을 먼저 복사해 읽기 전용 기준으로 대조하고, 신규 실행기는 시험 일정에서 결과를 나란히 기록한다. 교체 뒤 불일치가 생기면 신규 발행을 멈추고 승인본·원격 게시 ID·실패 단계부터 대조한다. 예전 직접 게시 진입점으로 돌아가기 전에 동일 확인 정책이 유지되는지 점검한다.
- **릴리스 전 시나리오.** ① 두 채널 중 하나만 성공 ② 외부 ID 응답이 끊긴 후 PC 재시작 ③ R2 공개 확인만 실패 ④ 사용자가 슬롯 시각 또는 플랫폼 변경 ⑤ 정상 슬롯 앞에 미확인 슬롯 ⑥ 대상 플랫폼에서 AI 표기 요청이 거절 ⑦ 이전 공용 도구 경로 없음. 각 시나리오에 외부 쓰기 수, 다음 재시도 대상, 사람이 보는 문구를 단언한다.
